# سای‌سای (SAI SAI)

نرم‌افزار فارسی، موبایل‌محور حسابداری، فروش و مدیریت موجودی برای کسب‌وکارهای ایران.

نام برند محصول: **سای‌سای (SAI SAI)**

واحد پول و تاریخ، گزارش‌ها و رابط کاربری با نیازهای بازار ایران طراحی می‌شوند.

## وضعیت فعلی
نسخه 0.1.0 — پوسته اولیه داشبورد RTL و موبایل‌فرست.

## مسیر توسعه
- داشبورد مالی
- فروش و فاکتور
- خرید
- موجودی و گردش کالا
- اشخاص و حساب‌ها
- دریافت و پرداخت
- هزینه‌ها
- گزارش‌های بازه‌ای
- پشتیبان‌گیری و بازیابی
- آماده‌سازی PWA و سپس بسته‌بندی موبایل

## اصول داده
- ثبت تراکنش‌ها باید قابل ردیابی باشد.
- موجودی از روی گردش‌های ثبت‌شده محاسبه شود.
- مبلغ‌ها با دقت عددی مناسب حسابداری نگهداری شوند.
- تاریخ شمسی در رابط کاربری پشتیبانی شود.
- ساختار برای حالت آفلاین‌اول طراحی شود.

این پروژه مستقل از پروژه PsychGame است.

## اشتراک ماهانه

ساختار اشتراک سای‌سای به‌صورت **server-verified** طراحی شده است؛ یعنی اپلیکیشن به‌تنهایی حق فعال‌کردن اشتراک را ندارد.

### کانال‌های پرداخت

- **نسخه وب/PWA:** درگاه مستقیم از طریق سرور.
- **نسخه کافه‌بازار:** خرید درون‌برنامه‌ای بازار در لایه Android، سپس ارسال purchase token به سرور سای‌سای برای تأیید.
- **نسخه مایکت:** خرید درون‌برنامه‌ای مایکت در لایه Android، سپس ارسال purchase token به سرور برای تأیید.

هر سه مسیر به یک اشتراک ماهانه و یک حساب کاربری متصل می‌شوند.

### قرارداد بک‌اند

- `POST /subscription/checkout` برای پرداخت وب.
- `POST /subscription/store/verify` برای تأیید خرید بازار/مایکت.
- `GET /subscription/status` برای دریافت وضعیت اشتراک.
- سرور باید کاربر، پلن، مبلغ و تاریخ انقضا را تعیین کند.
- توکن خرید فروشگاه باید در سرور با سرویس همان فروشگاه بررسی شود.
- فقط پس از تأیید معتبر، entitlement اشتراک فعال می‌شود.
- درخواست‌های تکراری باید idempotent باشند تا یک خرید دوبار ثبت نشود.
- کلیدها و اسرار بازار، مایکت و درگاه هرگز نباید داخل JavaScript فرانت‌اند قرار بگیرند.

### نکته فنی نسخه بازار

هسته فعلی سای‌سای با Vite/TypeScript ساخته شده است. برای نسخه بازار، رابط Android باید یک لایه Native برای SDK پرداخت بازار داشته باشد. این لایه خرید را انجام می‌دهد و نتیجه معتبر خرید را برای `verifyStorePurchase()` به سرور می‌فرستد. بنابراین بعداً با تغییر کانال انتشار، هسته حسابداری دوباره نوشته نمی‌شود.

درگاه واقعی تا زمان اتصال بک‌اند و حساب توسعه‌دهنده، عمداً شبیه‌سازی نمی‌شود.


## کنترل دسترسی با شماره موبایل (۶ حساب)

قابلیت مدیریت کاربران از مسیر **تنظیمات ← مدیریت کاربران مجاز (۶ نفر)** در دسترس است. مدیر اصلی می‌تواند حداکثر پنج شماره دیگر را فعال یا غیرفعال کند؛ مجموع حساب‌های فعال، با احتساب مدیر، حداکثر شش نفر است. هر کاربر باید مالکیت شماره خود را با کد پیامکی تأیید کند.

### راه‌اندازی امن در Supabase

1. متغیرهای `VITE_SUPABASE_URL` و `VITE_SUPABASE_ANON_KEY` را در محیط ساخت برنامه تنظیم کنید؛ کلید `service_role` هرگز نباید در برنامه قرار گیرد.
2. ابتدا migration پشتیبان ابری `supabase/migrations/202610090001_cloud_backups.sql` را در SQL Editor پروژه اجرا کنید.
3. سپس migration دسترسی `supabase/migrations/202610090002_phone_access_control.sql` را اجرا کنید.
4. قبل از ورود مدیر، شماره خودتان را به‌صورت بین‌المللی E.164 در SQL Editor ثبت کنید (کد کشور را جایگزین کنید):

   ```sql
   insert into public.saysay_access_users(phone, role, enabled)
   values ('+<YOUR_PHONE_WITH_COUNTRY_CODE>', 'owner', true);
   ```

5. ورود با شماره مدیر و تأیید پیامک را انجام دهید؛ بعد از آن می‌توانید پنج شماره دیگر را در صفحه مدیریت فعال کنید.
6. سرویس ارسال SMS و تأیید شماره تلفن را در تنظیمات Supabase Auth پیکربندی کنید.

فهرست مجاز و محدودیت شش حساب در پایگاه داده اعمال می‌شوند؛ مخفی‌کردن دکمه در رابط کاربری به‌تنهایی کنترل دسترسی محسوب نمی‌شود. شماره‌های غیرفعال‌شده دیگر اجازه استفاده از نسخه پشتیبان ابری را ندارند. این راه‌اندازی تا اجرای migrationها و پیکربندی SMS در پروژه Supabase عملیاتی نخواهد شد.
